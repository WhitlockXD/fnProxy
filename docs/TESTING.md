# 验收记录与实机待办

记录起始日期：2026-09-24；最新用户截图：2026-09-28。当前没有可由开发环境直接访问的 fnOS 测试机。下列用户截图和诊断报告是实机反馈；尚未通过独立抓包或出口对比验证宿主机代理路径。

用户提供的 0.1.0 安装截图显示：首页已打开，但样式和脚本未加载。原因是服务端只注册了 `/app/fnvpn`，未注册 `/app/fnvpn/` 下的静态资源路径。0.1.1 已修正路由并增加访问测试；新版在 fnOS 上的安装和页面行为仍待用户设备验证。

用户提供的 0.1.1 浏览器网络截图显示：订阅导入 `POST /app/fnvpn/api/import-url` 返回 403、`text/plain`、19 字节。该响应与应用的“来源校验失败”纯文本响应一致；旧校验要求 `Origin` 存在且与后端收到的 `Host` 一致，实际请求不满足这一条件。截图未显示完整请求头，尚不能区分 `Origin` 缺失与网关转发后 `Host` 不一致。0.1.2 改为检查管理员身份、JSON、自定义请求标记及浏览器跨站标记，API 错误统一返回 JSON。0.1.2 的导入行为仍待 fnOS 实测。

用户反馈 0.1.2 导入 Clash 订阅时显示“YAML 解析失败”。没有订阅响应样本，不能确定服务实际返回的格式。0.1.3 将订阅请求的客户端标识改为 Mihomo 默认的 `clash.meta`，并对网页、纯节点链接及 Base64 节点列表分别提示；Clash/Mihomo YAML 仍按原有安全边界解析与校验。0.1.3 的订阅导入仍待 fnOS 实测。

用户提供的 0.1.3 诊断报告记录 fnOS `1.2.0701`、内核 `6.18.18.c1107-trim`、`configured: false`、`running: false`、`tun_device: true`、无 IPv6 默认路由；`last_error` 为“存在无效的节点端口”。订阅原文未提供，不能断定端口无效的具体原因。0.1.4 会跳过端口无效的节点，保留其余可用节点，并显示跳过数量；当全部节点端口无效时，提示首个问题节点的序号和类型。对 Hysteria2 合法 `ports` 端口跳跃配置，允许缺少单个 `port`。

用户提供的 0.1.4 诊断报告显示 95 个节点已导入，Mihomo `v1.19.31` 和 `fnvpn0` 正在运行，TUN 规则已安装。fnOS 同时有优先级 `10` 的 `from [IP] lookup route_ens32` 源地址规则，排在 Mihomo 的 `19091` 规则之前。它可能使绑定 NAS 地址的请求绕过 TUN，但现有报告不能证明实际流量路径。0.1.5 增加四站点 HTTPS 连接测试，并比较普通路由与指定 NAS 源地址的路由；新包仍待用户设备验证。

用户提供的 0.1.5 诊断报告显示四个站点均在系统 DNS 解析阶段等待 8 秒后失败；`fnvpn0`、Mihomo 规则和路由表存在。由于还没有任何目标 IP，站点测试无法判断实际出站网卡。0.1.6 将普通 DNS 上游按规则经代理组访问，独立排除节点域名引导 DNS，并分别检测 Mihomo 本地 DNS 与引导 DNS；需要用户设备验证这是否恢复解析。

用户指出此前“规则模式”只设置私有地址直连，国内公网会落入代理组。0.1.7 在 `MATCH` 前加入随 FPK 固定的国内域名和国内 IP 规则集，并为命中的国内域名指定直连 DNS；规则数据与许可证已打包，启动前复制到 Mihomo 工作目录并进行配置校验。国内规则命中与实际出口仍需在 fnOS 上验证。

用户希望利用订阅中可能包含的规则。0.1.8 读取 YAML 顶层 `rules`，顺序采用可校验的域名、CIDR、国内 GEO 规则，保留直连和拒绝动作，代理动作映射到当前所选组；外部规则集和其他不支持的规则会跳过并计数。内置国内规则在订阅规则之后兜底。尚无用户订阅样本，无法判断该订阅实际是否包含规则；需要升级后手动更新订阅，核对界面采用／跳过数量与真实出口。

0.1.9 将桌面和页面名称改为 fnProxy，重新绘制分流图标。内部应用标识仍为 `fnvpn` 以保留升级路径，真机升级及设置保留情况仍需验证。

用户反馈升级 0.1.9 后，fnOS 桌面和应用中心仍显示旧图标，窗口左上角缺少图标。检查确认 0.1.9 FPK 根目录及 `app/ui/images` 均已包含新图标；但网页静态资源服务未放行 `icon.png`，因此应用窗口内的品牌图标会加载失败。0.1.10 放行该资源并添加 favicon，桌面入口改用新的图标文件名以避开旧资源路径缓存，同时验证 FPK 三处图标字节一致。应用中心图标可能由 fnOS 自身缓存，是否能通过原位升级刷新仍需实机确认；卸载重装前必须先保留订阅地址与设置。

用户提供的 0.1.10 实机截图见 [总览](screenshots/fnos-overview.png)、[节点与规则](screenshots/fnos-rule-mode.png) 和[连接诊断](screenshots/fnos-connectivity.png)。截图显示 fnProxy 窗口及图标、规则模式运行中的 TUN，诊断页四个站点的 HTTPS 连接均有响应，Mihomo 本地 DNS 与节点引导 DNS 均已答复。普通请求路由显示 `fnvpn0`；指定 NAS 地址的路由为“未知”。这些截图可证明页面和连接测试在该设备上工作，但不能独立证明每个站点实际经代理或直连，也不能证明应用中心图标已刷新。

## 真机验收时必须记录

先填写 fnOS 版本、App 版本、CPU 架构、内核版本、网卡和 IPv4／IPv6 默认路由、Docker 状态、NAS 管理入口与 SMB/NFS 使用情况。核实统一网关进程 UID，确认它与 FPK 的 Socket 许可设置匹配。测试机应有物理或带外恢复路径。

1. 手动安装 x86 FPK，确认 x86_64 架构检查、桌面入口和手机浏览器窗口、管理员鉴权与普通用户拒绝访问。首次启动确认路由、DNS、防火墙没有变化。
2. 导入有效 YAML，检查节点、组、模式、订阅规则采用／跳过数量与脱敏日志。对照订阅 YAML 验证国内直连、国外代理和显式拒绝规则的顺序；含远程 `RULE-SET` 的规则应显示跳过。依次测试 URL 超时、重定向、私网目标、无效 YAML；确认旧配置与管理页面继续可用。
3. 分别用公网 DNS 和局域网 DNS 配置测试：后者应明确阻止开启。开启 TUN 后，在诊断页核对 Mihomo 本地 DNS、节点引导 DNS、固定公网 IP 路由，再测试 YouTube、Google、GitHub 和百度；确认百度等命中国内规则集的网站经 Mihomo 选择 `DIRECT`，国外网站经所选代理组。比较普通路由与指定 NAS 地址的路由是否指向 `fnvpn0`，并对比开启前后的宿主机公网出口 IP。再检查 DNS 请求出口、局域网管理页面、网关及 SMB/NFS。浏览器在 30 秒内不能确认时，检查自动回滚。
4. 模拟节点不可达、强制终止 Mihomo、停止应用、重启、升级、卸载，逐项比对 `ip rule`、路由表、`fnvpn0`、DNS、管理页面和共享服务。验证本地恢复命令。
5. 用双网卡、Docker 已运行、IPv6 已启用和端口占用场景分别记录结果。IPv6 默认路由应明确阻止开启。Docker 和应用中心流量只能在独立抓包或出口检测后改为「已验证」。

所有真机验收结果应填写实测值、时间、执行者和证据位置；不能用 Windows 构建或普通 Linux 容器结果代替。
